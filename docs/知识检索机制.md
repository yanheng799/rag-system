# 知识检索机制

本文档详细分析 RAG 系统的知识检索实现机制，涵盖向量检索、BM25 全文检索、混合检索与 RRF 融合、分块合并、查询改写、Reranker 重排序、Prompt 构建、LLM 调用，以及编排器（Orchestrator）的完整流水线。

---

## 1. 整体架构

检索层采用 **Pipeline 设计**，每个节点独立可替换。整体数据流如下：

```
用户问题
  │
  ├─ 过滤条件解析（dataset_ids / doc_ids / doc_names → Milvus 表达式）
  │
  ├─ 查询改写（QueryRewriter，可选）→ 多个子查询
  │
  ├─ 多路检索（每个子查询独立执行）
  │     ├─ 向量检索（VectorSearcher）  ─┐
  │     └─ BM25 全文检索（BM25Searcher）─┤─ HybridSearcher
  │                                      ├─ RRF 融合
  │                                      └─ 分块合并（group_id）
  │
  ├─ Reranker 重排序（可选，仅 /retrieve 端点）
  │
  ├─ 多查询结果聚合（按 chunk_id 累加分数）
  │
  ├─ Prompt 构建（PromptBuilder）
  │
  ├─ LLM 流式调用（QwenClient）
  │
  └─ SSE 响应 + 查询日志
```

系统提供两个核心 API 端点：

| 端点 | 功能 | LLM | 流式 |
|------|------|-----|------|
| `POST /api/v1/query` | 完整 RAG 问答 | ✅ | ✅ SSE |
| `POST /api/v1/retrieve` | 纯检索（调试/评估用） | ❌ | ❌ |

## 2. 向量检索

**源文件**：`src/retrieval/vector_search.py`

### 2.1 工作流程

```
question → Embedder.embed_for_query() → 1024 维向量 → Milvus HNSW 搜索 → hit_to_chunk() → merge_grouped_chunks()
```

### 2.2 查询嵌入

`Embedder.embed_for_query()` 在问题前拼接 BGE 模型要求的指令前缀：

```
为这个句子生成表示以用于检索相关文章：{question}
```

模型为 `bge-large-zh-v1.5`（本地部署），输出 1024 维向量。

### 2.3 Milvus 索引配置

| 参数 | 值 | 说明 |
|------|---|------|
| 索引类型 | HNSW | 基于图的近似最近邻 |
| 距离度量 | COSINE | 余弦相似度 |
| M（连通度） | 16 | 每个节点的邻居数 |
| efConstruction | 200 | 构建时搜索宽度 |
| ef（查询时） | 128 | 查询时搜索宽度 |

### 2.4 过滤表达式

`MilvusStore._build_expr()` 将用户提供的 `filters` 字典和 `org_id` 组合为 Milvus 布尔表达式，支持 `==` 和 `in [...]` 操作符。

## 3. BM25 全文检索

**源文件**：`src/retrieval/bm25_search.py`

### 3.1 工作流程

```
question → Milvus BM25 原生搜索（内置分词 + BM25 评分）→ hit_to_chunk() → merge_grouped_chunks()
```

### 3.2 Milvus BM25 实现

Milvus 2.4+ 原生支持 BM25，通过 Schema 层的 `Function` 机制实现：

```python
Function(
    name="bm25_fn",
    input_field_names=["full_text"],
    output_field_names=["sparse_embedding"],
    function_type=FunctionType.BM25,
)
```

- `full_text` 字段（VARCHAR 65535）启用 `enable_analyzer=True`，Milvus 内置中文分词
- 自动生成 `sparse_embedding`（SPARSE_FLOAT_VECTOR）
- 索引：`SPARSE_INVERTED_INDEX`，算法 `DAAT_MAXSCORE`

### 3.3 BM25 参数

| 参数 | 值 | 说明 |
|------|---|------|
| k1 | 1.2 | 词频饱和度参数 |
| b | 0.75 | 文档长度归一化参数 |

## 4. 混合检索与 RRF 融合

**源文件**：`src/retrieval/hybrid_search.py`、`src/retrieval/rrf_fusion.py`

### 4.1 HybridSearcher

混合检索器同时调用向量检索和 BM25 检索，各自返回 `top_k` 条结果，然后通过 RRF 融合：

```python
vector_chunks = self._vector_searcher.search(question, top_k, filters, org_id)
bm25_chunks   = self._bm25_searcher.search(question, top_k, filters, org_id)
fused = rrf_fuse(vector_chunks, bm25_chunks)
```

### 4.2 RRF 融合算法

Reciprocal Rank Fusion 的核心公式：

```
score(d) = Σ  1 / (k + rank_i)
```

其中 `k` 为平滑常数（默认 60，取自 `settings.rrf_k`），`rank_i` 为文档 d 在第 i 路检索中的排名。

**具体实现**：

1. 遍历向量检索结果，记录每条结果的 `vector_rank` 和 `vector_score`
2. 遍历 BM25 检索结果：
   - 若 `chunk_id` 已存在于 score_map → 补充 `bm25_rank` 和 `bm25_score`
   - 若不存在 → 新增条目（`vector_rank=None`）
3. 对每条结果计算 RRF 分数：
   - 仅向量命中：`rrf_score = 1/(k + vector_rank)`
   - 仅 BM25 命中：`rrf_score = 1/(k + bm25_rank)`
   - 双路命中：`rrf_score = 1/(k + vector_rank) + 1/(k + bm25_rank)`
4. 保留原始 `vector_score` 和 `bm25_score` 在 `RetrievedChunk` 上，用于透明展示
5. 按 `rrf_score` 降序排列

**设计优势**：RRF 不依赖原始分数的绝对值或分布，仅使用排名，天然兼容不同检索路的异构分数体系。

## 5. 分块合并

**源文件**：`src/retrieval/chunk_merge.py`

### 5.1 问题背景

在摄取阶段，过大的段落会被拆分为多个子分块，共享同一个 `group_id`。检索时，如果某个子分块命中，需要将所有兄弟分块召回并重新组装为完整段落。

### 5.2 合并流程

```
检索命中列表
  │
  ├─ 按 group_id 分组
  │
  ├─ 调用 fetch_fn(group_ids) 从 Milvus 获取所有兄弟分块
  │
  ├─ 为尚未在结果中的兄弟创建 score=0.0 的 RetrievedChunk
  │
  ├─ 按 (page, chunk_index) 排序兄弟分块
  │
  └─ 合并：
       full_text  ← 换行拼接
       score      ← 取最大值
       image_urls ← 合并列表
       elements   ← 合并列表
       pages      ← 去重排序
```

### 5.3 hit_to_chunk

将 Milvus 原始命中字典转换为 `RetrievedChunk` 对象，解析 `ChunkMetadata` 并反序列化 `elements` 为 `ContentElement` 列表。

## 6. 查询改写

**源文件**：`src/orchestration/query_rewriter.py`

### 6.1 目的

将用户的单一问题扩展为多个语义等价但表述不同的子查询，提升召回率。

### 6.2 工作流程

1. 向 LLM 发送系统提示，要求生成两类子查询：
   - **语义改写**（2-3 条）：同义替换、换角度表述
   - **关键词查询**（1-2 条）：提取核心关键词
2. 数量由 `settings.query_rewrite_count`（默认 3）控制
3. 返回 `[原始问题, 子查询1, 子查询2, ...]`

### 6.3 降级策略

- LLM 调用失败 → 返回 `[原始问题]`
- 响应解析失败（先尝试 `json.loads`，再从 Markdown 代码块中提取 JSON 数组）→ 返回 `[原始问题]`

### 6.4 配置

| 配置项 | 默认值 | 说明 |
|-------|-------|------|
| `query_rewrite_enabled` | `True` | 是否启用查询改写 |
| `query_rewrite_count` | `3` | 子查询数量 |

## 7. Reranker 重排序

**源文件**：`src/retrieval/reranker.py`

### 7.1 模型

使用自部署的 `bge-reranker-large` 交叉编码器模型，通过 `/v1/rerank` API 调用。

### 7.2 工作流程

```
query + documents (top_k × rerank_fetch_multiplier)
  │
  ├─ POST /v1/rerank
  │     payload: { model, query, documents, top_n, return_documents: false }
  │
  └─ 返回 RerankResult(index, relevance_score) 按 relevance_score 降序
```

### 7.3 过召回策略

为弥补粗排阶段的精度损失，先过召回 `top_k × rerank_fetch_multiplier`（默认 3 倍）条结果，再通过 Reranker 精排截取 `top_n` 条。

### 7.4 降级容错

Reranker 调用失败时记录警告，返回空列表，系统回退到原始排序结果。

### 7.5 使用范围

| 端点 | 是否使用 Reranker |
|------|------------------|
| `/api/v1/query` | ❌ 未使用（直接使用混合检索结果） |
| `/api/v1/retrieve` | ✅ 可选（`use_reranker` 参数控制） |

## 8. Prompt 构建

**源文件**：`src/orchestration/prompt_builder.py`

### 8.1 System Prompt

角色设定为"电力工程领域问答助手"，核心约束：
- 严格基于参考资料回答
- 引用文档名称和页码
- 信息不足时明确说明

### 8.2 上下文构建

对每个检索命中的分块：

```
[参考资料{idx}: 《{filename}》第{page}页]
{分块中各 ContentElement 的 content 字段}
```

**注意**：仅提取 `ContentElement.content`（文本内容），`image_url` 不进入 LLM prompt。

### 8.3 最终消息格式

```python
[
    {"role": "system", "content": system_prompt},
    {"role": "user",   "content": "参考资料：\n{context}\n\n问题：{question}"}
]
```

## 9. LLM 客户端

**源文件**：`src/orchestration/llm_client.py`

### 9.1 架构

抽象基类 `LLMClient` 定义接口 `complete(messages, stream)`，具体实现 `QwenClient` 使用 DashScope OpenAI 兼容 API。

### 9.2 配置

| 配置项 | 值 | 说明 |
|-------|---|------|
| 模型 | `qwen3-max` | 通义千问旗舰模型 |
| API | DashScope `/chat/completions` | OpenAI 兼容接口 |
| temperature | 0.1 | 低随机性，偏向事实性回答 |
| max_tokens | 2048 | 最大输出长度 |
| timeout | 30s | 请求超时 |

### 9.3 流式输出

`stream=True` 时使用 `httpx.Client.stream()` 迭代 SSE 事件流：
- 解析 `data: {json}` 行，提取 `choices[0].delta.content`
- `data: [DONE]` 终止流
- 通过 `yield` 逐 token 返回

## 10. 编排器（Orchestrator）

**源文件**：`src/orchestration/orchestrator.py`

### 10.1 依赖注入

`RAGOrchestrator` 通过构造函数接收所有组件：

| 组件 | 类型 | 职责 |
|------|------|------|
| `searcher` | `VectorSearcher` 或 `HybridSearcher` | 检索 |
| `llm_client` | `LLMClient` | LLM 调用 |
| `prompt_builder` | `PromptBuilder` | Prompt 构建 |
| `doc_store` | `DocumentStorePort` | 文档元数据查询 |
| `query_rewriter` | `QueryRewriter`（可选） | 查询改写 |

### 10.2 query_stream 流水线

完整的 SSE 流式问答流程：

```
Phase 1: 查询改写
  SSE → status: {phase: "rewriting"}
  │
  ├─ query_rewriter.rewrite(question) → [question, sub1, sub2, ...]
  └─ 降级: [question]

Phase 2: 多路检索
  SSE → status: {phase: "retrieving"}
  │
  ├─ 对每个子查询执行 searcher.search()
  ├─ 按 chunk_id 累加分数（多次命中的分块分数叠加）
  ├─ 分数降序排列，截取 top_k
  └─ merge_grouped_chunks() 合并同组兄弟分块

Phase 3: 文件名解析
  │
  └─ 批量查询 PostgreSQL，将 doc_id 映射为真实文件名

Phase 4: Prompt 构建
  │
  └─ prompt_builder.build(question, chunks, filename_map)

Phase 5: LLM 流式生成
  SSE → token: {content}  (逐 token)
  │
  └─ llm.complete(messages, stream=True) → AsyncGenerator

Phase 6: 结果输出
  SSE → result: {sources, total_ms, rewritten_queries}
  │
  ├─ 构建来源信息（metadata + elements，图片 URL 代理化）
  └─ 写入查询日志到 PostgreSQL（含计时指标）
```

### 10.3 多查询搜索

`_multi_query_search(queries, top_k, filters, org_id)`：

- **单查询**：直接委托给 `searcher.search()`
- **多查询**：每个子查询独立检索，按 `chunk_id` 累加分数（重复命中的分块分数叠加），排序后返回 `top_k`

### 10.4 图片 URL 代理

所有返回给前端的 `image_url` 通过 `_build_response_sources()` 转换为代理路径：

```
内部路径: table-images/{doc_id}_p{page}_t{idx}.png
代理路径: /api/v1/images/table-images/{doc_id}_p{page}_t{idx}.png
```

后端 `/api/v1/images/{path}` 端点从 MinIO 获取图片后返回，避免暴露内部存储地址和签名过期问题。

## 11. API 请求/响应结构

### 11.1 查询接口（`POST /api/v1/query`）

**请求**：

| 字段 | 类型 | 默认值 | 说明 |
|------|------|-------|------|
| `question` | str | 必填 | 用户问题 |
| `top_k` | int (1-20) | 5 | 检索结果数 |
| `dataset_ids` | list[str] | 可选 | 数据集过滤 |
| `doc_ids` | list[str] | 可选 | 文档 ID 过滤 |
| `doc_names` | list[str] | 可选 | 文档名称过滤 |
| `show_rewritten` | bool | false | 是否返回改写后的查询 |

**SSE 响应事件流**：

```
event: status    data: {"phase": "rewriting"}
event: status    data: {"phase": "retrieving"}
event: token     data: {"content": "根"}
event: token     data: {"content": "据"}
...
event: result    data: {"sources": [...], "total_ms": 1234, "rewritten_queries": [...]}
```

### 11.2 检索接口（`POST /api/v1/retrieve`）

**请求**：

| 字段 | 类型 | 默认值 | 说明 |
|------|------|-------|------|
| `question` | str | 必填 | 用户问题 |
| `top_k` | int (1-50) | 10 | 检索结果数 |
| `search_mode` | str | `hybrid` | 检索模式：`vector` / `bm25` / `hybrid` |
| `dataset_ids` | list[str] | 可选 | 数据集过滤 |
| `doc_ids` | list[str] | 可选 | 文档 ID 过滤 |
| `doc_names` | list[str] | 可选 | 文档名称过滤 |
| `use_reranker` | bool | false | 是否启用 Reranker |
| `rerank_top_n` | int (1-50) | 5 | Reranker 返回数量 |

**响应**：

```json
{
  "question": "...",
  "search_mode": "hybrid",
  "total_retrieved": 10,
  "retrieval_ms": 234,
  "chunks": [
    {
      "rank": 1,
      "metadata": { "chunk_id": "...", "chunk_type": "...", "filename": "...", "page": 1 },
      "full_text": "...",
      "scores": {
        "vector_score": 0.95,
        "bm25_score": 12.3,
        "rrf_score": 0.032,
        "rerank_score": 0.98
      },
      "image_urls": ["..."]
    }
  ],
  "rewritten_queries": ["..."]
}
```

### 11.3 过滤条件解析

`resolve_filters()` 将三种过滤维度解析为 Milvus 查询表达式：

```
dataset_ids → 该数据集下所有 doc_id
doc_ids     → 直接使用
doc_names   → PostgreSQL 模糊查询 → doc_id
```

三种条件取交集，生成 `{"doc_id": [id1, id2, ...]}` 过滤表达式。

## 14. 关键设计决策

| 决策 | 说明 |
|------|------|
| **双路检索 + RRF 融合** | 向量检索捕捉语义相似性，BM25 捕捉关键词精确匹配，RRF 仅基于排名融合，天然兼容异构分数 |
| **查询改写** | 单一查询可能表述模糊，多查询扩展提升召回覆盖面；累加分数奖励多路命中的分块 |
| **group_id 分块合并** | 检索命中的子分块自动召回所有兄弟并重组为完整段落，保证上下文完整性 |
| **Reranker 可选且降级容错** | 精排模型作为可选增强，失败时回退到粗排结果，系统可用性优先 |
| **图片 URL 代理** | 前端通过 `/api/v1/images/{path}` 访问图片，后端从 MinIO 获取，避免签名过期和内部地址暴露 |
| **StoragePort 解耦** | 抽象接口隔离存储实现，Milvus/PostgreSQL/MinIO 可独立替换 |
| **Pipeline 可替换** | 每个检索节点（向量/BM25/混合/融合/合并）独立实现，可单独升级或替换 |
